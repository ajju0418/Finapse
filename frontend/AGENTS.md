# Finapse frontend rules

Project-wide rules live in [../AGENTS.md](../AGENTS.md). **Read that first** —
the domain and security rules apply here too. This file covers the frontend only.

> Everything above this line is generated by `next dev`. Leave it in place;
> deleting it only recreates an uncommitted change.

## Stack

Next.js 16 (App Router, Turbopack) · React 19 · TypeScript strict · Tailwind ·
shadcn/ui primitives in `components/ui/` · `lucide-react` icons.

Next.js 16 differs from older versions you may have memorised. Notably
`middleware.ts` is replaced by **`proxy.ts` exporting `proxy()`**. Check
`node_modules/next/dist/docs/` before relying on recalled API details.

## Layout

```
app/
  (auth)/login, (auth)/register    public routes
  app/<name>/page.tsx              authenticated routes, wrapped by AuthGuard
components/<domain>/               grouped by domain, not by type
components/ui/                     shadcn primitives — reuse, don't reinvent
lib/api/<domain>.ts                typed API clients
lib/utils/format.ts                formatCurrency, formatDate, formatShortDate
types/<domain>.ts                  shared types
```

Adding a page: create `app/app/<name>/page.tsx`, then add it to the `navItems`
array in `components/navigation/Sidebar.tsx` or it will be unreachable.

## Non-negotiables

### F1. All network calls go through `apiClient`

`lib/api/client.ts` handles bearer tokens, the shared single-flight 401 refresh,
and error normalisation. A bare `fetch` for a JSON endpoint will break auth.

Concurrent 401s must share one refresh promise — rotating the refresh token
twice trips the backend's replay detection and logs the user out.

File downloads are the one exception (see `lib/api/export.ts`), because the
response is a blob rather than JSON. Mirror that file's 401 retry.

### F2. Never persist the access token

It lives in memory in `lib/auth/token-store.ts`. `localStorage` and
`sessionStorage` are readable by any injected script. The refresh token is an
httpOnly cookie the JavaScript cannot see — that is the design.

### F3. Handle all four states

Every data-driven view needs loading, error, empty, and populated states. A
component that renders nothing while loading looks broken.

```tsx
if (loading) return <Skeleton className="h-44 rounded-xl" />
if (error)   return <p className="text-sm text-destructive">{error}</p>
if (items.length === 0) return <EmptyState … />
return <List items={items} />
```

Empty states say what to do next, not just that something is missing.
Good: *"Set a monthly cap for a category and Finapse will track it."*
Bad: *"No data."*

### F4. Format money with `formatCurrency`

Never `toFixed(2)` or string concatenation. It handles the Indian numbering
system (`₹1,20,000`, not `₹120,000`).

### F5. Types mirror the backend exactly

When a DTO changes, update `types/` in the same edit. Never use `any`; never
silence an error with `@ts-ignore`. `npm run build` type-checks and CI runs it.

### F6. Validate before enabling submit

Disable the submit button until input is valid and show why inline. Do not let
the user submit and discover the problem from a 400.

## Styling

Use semantic Tailwind tokens so theming works: `bg-card`, `text-muted-foreground`,
`border-border`, `text-destructive`, `bg-primary`. Avoid raw colours like
`bg-gray-800`.

Convention: `rounded-xl` cards, `border border-border bg-card`, `p-5`,
`text-sm` body, `text-xs` for secondary text.

## Accessibility

Icon-only buttons need `aria-label`. Inputs need a real `<label>`. Use
`<button type="button">` inside forms unless the button submits.

## Testing

There is no frontend test suite yet. Until there is, verify by running
`npm run build` and exercising the page in the browser. Do not claim a UI works
without loading it.
